# Архитектура

Как система устроена внутри: из чего состоит, как хранит данные и по каким
правилам их меняет. Почему выбрано именно так — в [решениях](DECISIONS.md).

## Три части и поток данных

**Расширение** живёт в профиле AdsPower. При загрузке страницы Ads Manager
content-script ищет в разметке токен вида `EAA…`, предпочитая самый «сильный»
из найденных, и обходит им Graph API v24: сначала `me`, затем бизнес-менеджеры
и их рёбра — собственные и клиентские кабинеты, страницы, пиксели, дочерние
БМ, сотрудники. Отдельно берутся личные кабинеты и страницы аккаунта.

Собранное уходит одним POST на `/api/ingest` вместе с общим секретом. Ключей
от базы у расширения нет: даже если файл расширения попадёт не в те руки, это
даст возможность писать инвентарь, но не читать базу.

Один аккаунт отправляется не чаще раза в час. Отметка времени ставится только
после успешного ответа — если сервер недоступен, следующая вкладка попробует
снова, а не будет ждать час впустую.

**Сервер** — один процесс Node. Он отдаёт статику приложения, обслуживает его
API, держит WebSocket-соединения и принимает инвентарь. Состояния в памяти он
не хранит, кроме списка открытых сокетов.

**Приложение** — одна страница. Она ничего не знает ни про HTTP, ни про базу:
всё общение идёт через два объекта, которые подкладывает слой хранилища.

## Модель данных

Вся база — одна таблица PostgreSQL:

```sql
docs (collection text, id text, data jsonb, updated_at timestamptz)
```

Ключ — пара «коллекция плюс идентификатор». Набор колонок у таблиц свободный и
меняется людьми на ходу, поэтому раскладывать содержимое по столбцам нечего.

Адресация повторяет привычную иерархию: коллекция — нечётное число сегментов
пути, документ — чётное.

| Путь | Что лежит |
| --- | --- |
| `tables/{tid}` | описание таблицы: имя, порядок, колонки |
| `tables/{tid}/rows/{rid}` | строка данных |
| `views/{vid}` | вид: фильтры, сортировка, скрытые колонки, подкраска |
| `log/{ключ}` | лог действий, пачками по дате и сессии |
| `limits/{ключ}` | суточный счётчик удалений для менеджеров |

Обращаться можно только к этим четырём корням. Пользователи лежат в отдельной
таблице и через это API недоступны вообще.

### Строка данных

```json
{
  "c":   { "c_fbname": "Polina", "c_login": "…", "c_amount_spent": 1284.3 },
  "o":   10,
  "at":  "2026-09-17T…", "by":  "Админ",
  "uat": "2026-09-17T…", "uby": "авто-синк"
}
```

Все значения ячеек лежат в `c`, ключи — идентификаторы колонок из описания
таблицы. Остальное служебное: порядок строки, кто и когда создал и менял.
Поле `del` помечает запись как лежащую в корзине.

### Детерминированные идентификаторы

Документы ассетов адресуются по идентификатору из Facebook, а не случайным
ключом. Благодаря этому повторный сбор того же аккаунта перезаписывает
записи, а не плодит копии.

| Префикс | Что это |
| --- | --- |
| `fb_` | аккаунт, с которого шёл сбор |
| `aa_` | рекламный кабинет |
| `bm_` | бизнес-менеджер |
| `fp_` | страница |
| `px_` | пиксель |

Связи между таблицами хранятся массивами этих же идентификаторов: у кабинета
`c_acc` содержит `["fb_100077…"]`, а `c_bm` содержит `["bm_9001"]`. Приложение
показывает их подписями строк, на которые они указывают.

### Восемь таблиц

Схема описана кодом в [`scripts/schema.js`](../scripts/schema.js) и
раскладывается в базу при первом запуске.

| Таблица | Что в ней | Кто заполняет |
| --- | --- | --- |
| `t_acc` | аккаунты (профили) | автосбор, плюс руками доступы, байер, статус |
| `t_ads` | рекламные кабинеты | автосбор |
| `t_bm` | бизнес-менеджеры | автосбор |
| `t_fp` | страницы | автосбор |
| `t_pixel` | пиксели | автосбор |
| `t_card` | карты | руками |
| `t_soc` | соцсети | руками |
| `t_log` | раздача страниц | руками |

## Слой хранилища: главная граница

Приложение обращается к данным **только** через два объекта, которые создаёт
[`public/adapter.js`](../public/adapter.js):

```js
window.__DB__        // collection(path) → onSnapshot, add, get
                     // doc(path)        → get, set, update, delete
window.__AUTH__      // onChange, user, getRole, signOut
```

Семь операций, больше ничего. Именно поэтому переезд с Firebase на свой сервер
не потребовал переписывания приложения: заменился слой под ним, а страница на
полторы тысячи строк осталась прежней.

Если менять бэкенд снова, менять надо ровно этот файл.

## Правила частичного обновления

Операция `update` — это **глубокое слияние**, и на нём держится сохранность
данных:

- объекты сливаются рекурсивно;
- массивы заменяются целиком;
- `null` удаляет поле;
- всё остальное заменяет значение.

Три случая, ради которых это важно:

```js
update({c: {c_status: "active"}})     // меняет ячейку, соседние не трогает
update({cols: {c_x: {order: 15}}})    // двигает колонку, сохраняя имя и тип
update({del: null})                   // возвращает запись из корзины
```

Слияние делает сервер ([`server/lib/merge.js`](../server/lib/merge.js)) внутри
транзакции с блокировкой строки, поэтому две одновременные правки разных ячеек
не затирают друг друга.

Автосбор пишет по тем же правилам. Поэтому он обновляет данные из Facebook и
не трогает то, что люди заполнили руками: логины, пароли, коды двухфакторной
аутентификации, заметки, байера. Пустые значения он не пишет вовсе — иначе
слияние затирало бы содержимое пустотой.

## Живые обновления

Подписка на снимки коллекции из прежней версии заменена на WebSocket.
Протокол простой.

Клиент подписывается и отписывается:

```json
{"sub": ["tables", "tables/t_acc/rows"]}
{"unsub": ["tables/t_acc/rows"]}
```

Сервер после каждой записи шлёт подписчикам изменившийся документ:

```json
{"t": "change", "c": "tables/t_acc/rows", "id": "fb_100077…", "data": {}}
{"t": "delete", "c": "tables/t_acc/rows", "id": "fb_100077…"}
```

Адаптер держит кэш коллекции, применяет дельты и отдаёт приложению полный
список документов — форму, которую оно ждёт.

Две тонкости, без которых теряются правки:

- подписка оформляется **до** первой выборки, а пришедшие тем временем
  изменения складываются в буфер и применяются после неё;
- после обрыва коллекции перечитываются целиком, потому что за время
  переподключения данные могли уйти вперёд.

Если сокет не поднялся вовсе — сети нет, мешает прокси или блокировщик, —
адаптер переходит на периодический опрос. Медленнее, но данные не застывают.

## Вход и роли

Пароли хешируются встроенным в Node алгоритмом `scrypt`. Сессия — подписанный
HMAC небольшой объект в cookie с флагами `HttpOnly`, `SameSite=Lax` и `Secure`
за прокси. Внешних сервисов и нативных зависимостей нет.

| Роль | Что может |
| --- | --- |
| `admin` | всё: аналитика, архив таблиц, переименования |
| `manager` | правит данные, не больше десяти удалений в сутки |
| `viewer` | только чтение |

Права проверяются на сервере функцией `canWrite` в
[`server/lib/auth.js`](../server/lib/auth.js). Отдельно оговорено: лог действий
не удаляет никто, включая администратора, потому что в нём лежат копии стёртых
записей. Убрать таблицу целиком может только администратор, а строки удаляет и
менеджер.

## Интерфейс сервера

| Метод и путь | Зачем |
| --- | --- |
| `POST /api/auth/login`, `logout`, `GET /api/auth/me` | вход, выход, кто я |
| `GET /api/collection?path=…` | список документов коллекции |
| `POST /api/collection?path=…` | создать документ со сгенерированным ключом |
| `GET /api/doc?path=…` | прочитать документ |
| `PUT /api/doc?path=…` | записать целиком |
| `PATCH /api/doc?path=…` | слить частично |
| `DELETE /api/doc?path=…` | удалить |
| `GET /api/health` | состояние сервера и базы |
| `WS /api/live` | живые обновления |
| `POST /api/ingest` | приём инвентаря от расширения |

Путь документа передаётся параметром запроса, а не частью маршрута: в нём есть
слэши и такие символы, как тильда в ключах лога.

Приёмник инвентаря стоит особняком: он не требует входа, проверяет общий
секрет и отвечает заголовками CORS, потому что запрос приходит со страницы
Facebook.

## Переменные окружения

| Переменная | По умолчанию | Зачем |
| --- | --- | --- |
| `DATABASE_URL` | нет | подключение к PostgreSQL; иначе берутся `PGHOST`, `PGUSER` и прочие |
| `SESSION_SECRET` | нет | подпись сессий, обязательна |
| `SYNC_SECRET` | нет | общий секрет с расширением; без неё приём выключен |
| `BOOTSTRAP_ADMIN` | нет | почта и пароль первого администратора, на один раз |
| `PORT` | `3000` | должен совпадать с `containerPort` в `amvera.yml` |
| `PGPOOL_MAX` | `5` | предел подключений к базе |
| `PGSSL` | по адресу базы | принудительно включить или выключить шифрование |
| `PUBLIC_DIR` | `../public` | откуда отдавать приложение |
